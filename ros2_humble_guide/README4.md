# 03. 실기체 실습 — 네트워크 설정부터 픽앤플레이스까지

**목표**
1. PC ↔ RM75 이더넷 연결과 드라이버 설정을 완료한다.
2. 실물 팔을 상대로 토픽·서비스·액션을 다루고, 직접 교시(드래그 티칭)를 체험한다.
3. 제조사 기본 모션 명령(MoveJ · MoveJ_P · MoveL)을 실행하고 MoveIt2와의 차이를 눈으로 확인한다.
4. MoveIt2로 실물을 계획·실행하고, 최종 미션 **픽앤플레이스**를 완수한다.

---

## 0. 안전 수칙 — 실기체 앞에 서기 전에 (필독)

**3대 수칙**
1. 워크스페이스 제한이 설정된 상태에서만 운용한다.
2. **동작 중 작업 공간(팔이 닿는 반경 약 610 mm)에 손을 넣지 않는다.**
3. **그리퍼 손가락 사이에 손가락 절대 금지.**

충돌 보호 기능(관절 전류 감시 → 자동 정지)이 있지만, 그것은 **최후의 보호막**이지 손을 넣어도 되는
이유가 아니다.

**역할 3인 체계** — 실기체 조작은 항상 세 역할로 진행하고, 시도마다 로테이션한다:
- **조작자**: RViz/코드 실행 담당
- **비상정지 전담**: 외부 정지 버튼 옆, 조작에 참여하지 않고 팔만 주시
- **모니터링·기록**: `ros2 topic echo /joint_states` 감시 + 영상·로그 기록

**표준 절차(SOP) 요약** — 각 단계 완료를 소리 내어 콜하고 다음으로:

| # | 절차 | 콜 |
|---|---|---|
| ① | 사전 체크 (담당자 동석 · 비상정지 위치 · 작업 공간 정리 · 실행할 코드 설명 가능) | "체크 완료" |
| ② | 작업 공간에 사람·물체 없음 확인 (Scene에 등록 안 된 실물이 남아 있지 않은가) | "작업 공간 확인" |
| ③ | 전원 투입 · 상태 정상 · `/joint_states` 수신 확인 | "상태 정상" |
| ④ | **시뮬 검증된 모션만** 실기체로: Plan → 잔상 확인 → 콜 → Execute | "잔상 확인 — 실행합니다" |
| ⑤ | 보호 정지 발생 시: 손대지 말고 담당자 호출, 무엇을 하다 멈췄는지 기록 | "보호 정지" |
| ⑥ | 종료: 홈 복귀 → 그리퍼 열기 → 전원 차단 | "종료 절차 완료" |

이상(이상 소음 · 예상과 다른 움직임 · 모니터링 끊김)이 감지되면 **멈추고 보고**한다.
"조금 이상하지만 계속"은 존재하지 않는 선택지다. 오탐 보고는 싸고, 놓침은 비싸다.

> 전원 투입, 보호 등급 설정, 교시 모드 전환, 에러 복구는 **담당 선배가 수행**한다.
> 신입생의 역할은 계획·실행·관찰·기록이다.

## 1. 네트워크 설정

구성: `PC (유선) ── 이더넷 케이블 ── RM75 베이스`

### 1-1. PC 유선 IP를 수동으로 설정

로봇 컨트롤러의 공장 기본 IP는 **192.168.1.18**이다. PC를 같은 대역으로 맞춘다.

- Ubuntu 설정 → 네트워크 → 유선 → 톱니바퀴 → IPv4 탭 → **수동(Manual)**
  - 주소: `192.168.1.100` / 넷마스크: `255.255.255.0` / 게이트웨이: 비움
- 적용 후 케이블을 뽑았다 꽂고 확인:

```bash
ip addr show          # 유선 인터페이스에 192.168.1.100 이 붙었는지
ping 192.168.1.18     # 로봇 전원이 켜져 있으면 응답이 와야 함
```

ping이 안 되면: 케이블·로봇 전원·PC IP 대역(192.168.1.x)·유무선 혼동을 순서대로 점검.

### 1-2. rm_driver 설정 파일 수정

```bash
gedit ~/ros2_ws/src/ros2_rm_robot/rm_driver/config/rm_75_config.yaml
```

두 항목을 확인/수정한다 (줄 번호는 버전마다 다르니 키 이름으로 찾는다):

| 키 | 값 | 의미 |
|---|---|---|
| `arm_ip` | `"192.168.1.18"` | 로봇 컨트롤러의 IP — 드라이버가 명령을 보낼 주소 |
| `udp_ip` | `"192.168.1.100"` | **PC의 유선 IP** — 로봇이 상태(관절값 등)를 UDP로 밀어 넣을 주소 |

> `udp_ip`가 틀리면 명령은 가는데 `/joint_states`가 안 들어오는, 헷갈리는 상태가 된다.
> "상태가 안 보이면 udp_ip부터"를 기억해 두자.

**수정 후 재빌드 필수** — C++ 패키지라 yaml 수정도 빌드해야 install에 반영된다:

```bash
cd ~/ros2_ws
colcon build --packages-select rm_driver
source install/setup.bash
```

## 2. 실기체 토픽·서비스·액션 다뤄보기

시뮬레이션에서 익힌 조사 루틴을 실물에 그대로 적용한다. 이 절은 **팔을 움직이지 않고 읽기만** 한다.

드라이버만 실행:

```bash
ros2 launch rm_driver rm_75_driver.launch.py
```

새 터미널에서:

```bash
# ① 토픽 지도 그리기 — rm_driver 네임스페이스의 토픽들이 대거 보인다
ros2 topic list -t
ros2 topic list | grep rm_driver | head -30
```

관찰 포인트: `/rm_driver/xxx_cmd` 와 `/rm_driver/xxx_result` 가 **짝**을 이룬다 —
명령 토픽에 발행하면 결과 토픽으로 성공/실패가 회신되는 구조다. 4절에서 이 구조를 그대로 쓴다.

```bash
# ② 관절 상태 — 실물의 각도가 들어온다
ros2 topic echo /joint_states --once
ros2 topic hz /joint_states

# ③ 메시지 구조 — RealMan 전용 메시지들 구경
ros2 interface list | grep rm_ros_interfaces | head -20

# ④ 노드/서비스/액션
ros2 node list
ros2 param list /rm_driver          # 드라이버 파라미터 (arm_ip 등이 보인다)
ros2 service list -t | head -20
ros2 action list -t
```

**effort 관찰 (시뮬 vs 실물)** — `/joint_states`의 `effort`가 시뮬레이션과 달리
**정지 상태에서도 0이 아닌** 것을 확인하자. 자기 무게(중력)를 버티는 힘의 전류 기반 추정치다.
RM75 기본형에는 관절 토크 센서가 없어 참값 토크가 아닌 **간접값**이며, 충돌 보호가 감시하는
바로 그 신호다. 모니터링 담당은 정지 상태의 값을 **기준선**으로 익혀 둔다 —
"비정상적으로 크다"는 기준선이 있어야 판정할 수 있다.

## 3. 직접 교시(드래그 티칭) 체험

같은 팔이 모드에 따라 완전히 다른 "성격"을 보이는 것을 몸과 데이터로 확인한다.
**모드 전환은 담당 선배가 티칭 소프트웨어로 수행**하고, 체험은 안내에 따라 진행한다.

| 체험 | 내용 | 관찰 |
|---|---|---|
| ① 위치 제어 상태 | 팔을 **살짝** 밀어 본다 | 버틴다. 무리하게 밀면 충돌 보호가 작동해 정지 — 그것을 확인하는 것까지가 체험 |
| ② 직접 교시 상태 | 팔을 손으로 이끈다 | 부드럽게 따라오고, 놓으면 그 자리에 머문다. 일곱 관절이 고루 순응하는지도 관찰 |
| ③ 재생 (가능 시) | 교시한 자세/궤적을 저장·재생 | 사람의 시연이 로봇의 동작이 되는 과정 (teaching by demonstration의 최소 형태) |

**동시에 모니터링 담당은** `ros2 topic echo /joint_states`를 띄워 두고 세 국면을 비교 기록한다:

| 국면 | position | velocity | effort |
|---|---|---|---|
| 정지 (교시 전) | 변화 없음 | 0 부근 | 중력을 버티는 기저값 (자세마다 다름) |
| 교시 중 | 손을 따라 연속 변화 | 손 속도만큼 비영 | 기저값 위에서 흔들림 — 사람이 준 힘의 그림자 |
| 재생 중 | 교시 궤적을 다시 그림 | 부드러운 프로파일 | 기저값 부근 복귀 — 힘의 주인이 로봇으로 |

> 이 체험이 뒤의 픽앤플레이스에서 실제로 쓰인다 — 그리퍼 길이 실측(6-2절)을 드래그 티칭으로 한다.

## 4. 제조사 기본 모션 명령 — MoveJ · MoveJ_P · MoveL

로봇 팔이 "원래 알아듣던 말"이다. 베이스 내장 컨트롤러의 기본 명령을 `rm_driver` 토픽으로 직접
호출해 보고, MoveIt2와의 차이를 눈으로 확인한다.

### 4-1. 개념 (교재 4.1절 요약)

| 명령 | 목표를 주는 방식 | 경로 |
|---|---|---|
| **MoveJ** | 7개 관절의 목표 각도 | 관절 공간 보간 — 손끝은 완만한 **곡선**. 빠르고 무리가 적어 "일단 저기로"의 기본값 |
| **MoveL** | 손끝의 목표 위치·자세 | 작업 공간의 **직선**. 수직 접근·긋기처럼 경로 자체가 중요할 때. 특이점 근처에서 실패·정지 가능 |
| **MoveJ_P** | 손끝의 목표 위치·자세 | 도착점은 데카르트, 이동은 관절식 — 경로보다 **도착점**이 중요할 때 |

세 명령의 공통 성격: ① **결정적**(같은 명령 = 항상 같은 경로) ② **즉시 실행**(호출이 곧 움직임 —
Plan/Execute 분리 없음) ③ **장애물을 모름**(충돌 검사 없음).

> ⚠️ **바로 이 ②③ 때문에 이 절이 가장 위험하다.** 잔상 확인 단계가 없다 = 발행 즉시 팔이 움직인다.
> - 작업 공간을 **완전히 비운다** (테이블 위 물건 포함)
> - `speed`는 **10~20** (%)으로
> - 비상정지 전담이 자리에 있는지 확인 후 발행
> - 한 번에 큰 각도 변화 금지 — 현재 자세에서 조금씩

### 4-2. 준비 — 메시지 구조부터 확인

드라이버가 떠 있는 상태(2절)에서, **발행 전에 반드시** 메시지 구조를 확인한다.
필드 이름·구성은 드라이버 버전에 따라 다를 수 있으므로, 아래 예시가 오류를 내면
`interface show` 출력에 맞춰 필드를 더하거나 뺀다.

```bash
ros2 interface show rm_ros_interfaces/msg/Movej
ros2 interface show rm_ros_interfaces/msg/Movejp
ros2 interface show rm_ros_interfaces/msg/Movel
```

결과 회신을 받을 터미널을 미리 켜 둔다:

```bash
# 터미널 A (결과 대기)
ros2 topic echo /rm_driver/movej_result
```

### 4-3. MoveJ — 관절 각도로 이동

```bash
# 터미널 B — 라디안 단위 7관절, 속도 10%
ros2 topic pub --once /rm_driver/movej_cmd rm_ros_interfaces/msg/Movej \
"{joint: [0.0, 0.3, 0.0, 0.6, 0.0, 0.6, 0.0], speed: 10, block: true, trajectory_connect: 0, dof: 7}"
```

- 손끝이 **완만한 곡선**을 그리며 이동하는 것을 관찰.
- 터미널 A에 `data: true`가 찍히면 성공.
- **같은 명령을 한 번 더** 보내 보자 — 경로가 완전히 동일하다(결정적). MoveIt과의 결정적 차이.

### 4-4. 현재 말단 자세 읽기 (MoveL/MoveJ_P 목표 만들기)

임의의 좌표를 지어내지 말고, **현재 자세를 읽어서 조금만 바꾼 목표**를 쓴다 — 도달 불가/이상
자세 사고를 예방하는 요령이다.

```bash
ros2 topic list | grep -i state     # 상태 조회 계열 cmd/result 토픽 짝을 찾는다
```

`get_current_arm_state` 계열의 cmd/result 짝이 보이면: result를 echo해 둔 상태에서 cmd에 빈
메시지를 발행 → 현재 관절값과 말단 pose(위치 m + 자세)를 회신받는다. (정확한 토픽/메시지 이름은
버전에 따라 다르므로 `interface show`로 확인해 사용.)

### 4-5. MoveJ_P / MoveL — 손끝 자세 목표

4-4에서 읽은 현재 pose에서 **z만 ±0.05 m** 바꾼 목표를 만든다. 아래는 형식 예시일 뿐,
숫자는 반드시 **내가 읽은 현재값** 기반으로 채운다:

```bash
# MoveJ_P — 도착점만 데카르트, 이동은 관절식
ros2 topic pub --once /rm_driver/movej_p_cmd rm_ros_interfaces/msg/Movejp \
"{pose: {position: {x: <현재x>, y: <현재y>, z: <현재z + 0.05>},
         orientation: {x: <현재qx>, y: <현재qy>, z: <현재qz>, w: <현재qw>}},
  speed: 10, block: true}"

# MoveL — 같은 두 점을 '직선'으로 (결과 토픽: /rm_driver/movel_result)
ros2 topic pub --once /rm_driver/movel_cmd rm_ros_interfaces/msg/Movel \
"{pose: {position: {x: <현재x>, y: <현재y>, z: <현재z - 0.05>},
         orientation: {x: <현재qx>, y: <현재qy>, z: <현재qz>, w: <현재qw>}},
  speed: 10, block: true}"
```

- MoveL 실행 중 특이점 근처에서 멈추면 정상적인 보호 동작이다 — 목표를 바꾸거나 MoveJ_P로 대체.
- 참고: `rm_example` 패키지에 같은 명령들의 C++ 예제가 있다 —
  `ros2 pkg executables rm_example`로 목록 확인, 소스(`rm_example/src`)는 코드로 토픽을 발행하는
  좋은 참고 자료다.

### 4-6. 그리퍼 명령 — 세 가지 숫자 (폭·속도·힘)

픽앤플레이스 전에 그리퍼 단독으로 확인해 둔다. **손가락 사이에 아무것도(특히 손) 없는 상태**에서:

```bash
ros2 interface show rm_ros_interfaces/msg/Gripperset
ros2 interface show rm_ros_interfaces/msg/Gripperpick

# 열기 (position 1~1000, 1000 = 최대 개방)
ros2 topic pub --once /rm_driver/set_gripper_position_cmd rm_ros_interfaces/msg/Gripperset \
"{position: 1000, block: true, timeout: 10}"

# 위치 제어로 부분 닫기
ros2 topic pub --once /rm_driver/set_gripper_position_cmd rm_ros_interfaces/msg/Gripperset \
"{position: 200, block: true, timeout: 10}"

# 힘 제어 파지 — 지정한 힘을 계속 유지 (실제 파지에 쓰는 명령)
ros2 topic pub --once /rm_driver/set_gripper_pick_on_cmd rm_ros_interfaces/msg/Gripperpick \
"{speed: 200, force: 300, block: true, timeout: 10}"

# 다시 열기
ros2 topic pub --once /rm_driver/set_gripper_position_cmd rm_ros_interfaces/msg/Gripperset \
"{position: 1000, block: true, timeout: 10}"
```

> **왜 파지에는 pick_on(힘 제어)인가** — 위치 제어로 닫으면 물체에 막힐 때 과부하 보호로 멈추면서
> 힘을 유지하지 않아 이송 중 미끄러진다. `pick_on`은 설정한 힘을 계속 유지한다.
> 힘이 약하면 놓치고, 강하면 물체가 손상된다 — 픽앤플레이스에서 이 값을 튜닝한다.

### 4-7. 관찰 기록 (교재 6.4절)

한 줄로 남긴다 — "같은 두 점을 잇는 길이 명령마다 달랐다. MoveJ는 ___, MoveL은 ___,
MoveIt2는 ___." 다음 절에서 MoveIt으로 같은 목표를 실행해 세 번째 빈칸을 채운다.

## 5. MoveIt2 실습 (실기체)

> ⚠️ **드라이버 중복 실행 금지** — 4절까지 쓰던 `rm_75_driver.launch.py` 터미널을 **Ctrl+C로 종료**한
> 뒤 진행한다. bringup이 드라이버를 포함하고 있어, 중복 실행하면 통신이 꼬인다.

```bash
ros2 launch rm_bringup rm_75_bringup.launch.py
```

드라이버 + MoveIt + RViz가 함께 뜬다. 시뮬레이션에서 하던 것과 화면은 같지만 **Execute가 실물을
움직인다**는 것이 유일하고 결정적인 차이다.

### 5-1. 첫 Plan & Execute

1. RViz MotionPlanning → Planning 탭에서 **Velocity Scaling / Accel Scaling = 0.1** 설정 (필수)
2. 마커를 현재 자세에서 **가까운 곳**으로 이동 → **Plan**
3. 잔상 애니메이션을 눈으로 확인 → "잔상 확인 — 실행합니다" 콜 → **Execute**
4. 실물 팔이 잔상대로 움직이는지 확인. 4-7의 세 번째 빈칸(MoveIt2는 ___)을 채운다 —
   같은 목표를 여러 번 Plan하면 경로가 달라질 수 있고, 실행 전 계산·확인 단계가 끼어든다.

**Scene에 테이블 등록 습관** — Scene 탭에서 실물 테이블 위치·크기로 Box를 추가한다.
Planning Scene에 등록되지 않은 실물은 플래너에게 보이지 않는다 — 등록해야 회피 대상이 된다.

### 5-2. 홈 자세 정하고 기록하기 (픽앤플레이스 준비물 ①)

작업하기 좋은 홈 자세의 조건: 관절이 한계에서 멀고, 팔꿈치가 적당히 굽어 있고(완전히 펴거나
꺾인 자세는 이후 계획 실패가 잦다), 작업 테이블을 내려다보는 자세.

RViz로 그 자세까지 Plan & Execute한 뒤 값을 기록한다:

```bash
ros2 topic echo /joint_states --once        # → 7개 position 값을 기록 (홈 관절값)
ros2 run tf2_ros tf2_echo base_link Link7   # → 말단 위치·자세 (좌표 감각 익히기)
```

> `tf2_echo`가 처음에 "frame does not exist"를 출력하다가 잠시 후 값이 나오는 것은 정상이다
> (TF 버퍼가 차는 시간).

## 6. 픽앤플레이스 실습 — 최종 미션

**미션**: 테이블 위 지정 위치 A의 물체를 집어 위치 B에 내려놓는다.
인지(물체가 어디 있는가)는 이번엔 **사람이 자로 재서** 담당한다 — 이 수동 인지를 카메라가
대신하게 만드는 것이 다음 단계(비전 기반 조작)다.

**성공 기준을 시작 전에 합의**한다 (예: "물체가 B 표식 반경 5 cm 안에 세워진 채 놓이고,
낙하·충돌 없이 홈 복귀까지 — 3회 중 2회 이상"). 애매한 기준은 애매한 회고를 낳는다.

**진행 순서**: ① 시뮬레이션 검증 → ② 실측 3종 → ③ 실기체 실행 → ④ 튜닝·기록

### 6-1. 시뮬레이션 검증 (필수 관문)

02에서 만든 그리퍼 포함 설정으로 전체 시퀀스를 먼저 완주한다.

```bash
# 터미널 1
ros2 launch rm_75_jaw_config demo.launch.py

# 터미널 2 — 이 가이드 폴더에서
python3 scripts/pick_place.py
```

`pick_place.py`가 하는 일: 테이블·블록을 Scene에 등록 → **pick**(접근 → 그리퍼 열기 → 하강 →
부착 → 닫기 → 상승) → **place**(이송 → 하강 → 열기 → 살짝 후퇴 → 분리 → 후퇴).
읽어 볼 포인트:

- 모든 팔 이동이 `plan 성공 확인 → execute` 구조다 — 실패한 계획은 실행하지 않는다.
- **attach는 그리퍼를 닫기 전에** — 부착(touch_links)이 "손가락이 이 물체에 닿아도 됨"이라는
  허가증이라, 닫아서 접촉이 생기기 전에 발급해야 한다.
- **detach는 손가락이 물체에서 완전히 빠진 뒤에** — place에서 열기 → 살짝 후퇴 → 분리 순서인 이유.
  (순서를 바꾸면 "그리퍼 열기 실패"로 시퀀스가 중단된다 — 실제로 겪었던 버그다.)
- RViz에서 그리퍼가 유령처럼 겹쳐 보이면 Planning Request → Query Goal State 체크 해제.

이어서 **파라미터화된 검증 하네스**로 실물 조건을 미리 재현해 본다:

```bash
python3 scripts/grasp_test.py --help    # 옵션 설명

# 예: 실물 물통 조건 재현 (베이스보다 11.5cm 낮은 테이블, 전방 54.6cm, 측면 파지)
python3 scripts/grasp_test.py --shape box --pos 0.5459 0.0 \
  --size 0.055 0.055 0.21 --table-z -0.115 --grasp-dir front

# 예: 지름 6cm 높이 18cm 원기둥을 위에서 파지, 위치 바꿔가며 반복
python3 scripts/grasp_test.py --pos 0.45 0.10 --radius 0.03 --height 0.18
```

grasp_test가 보여주는 설계 포인트: 파지점 = 물체 **몸통 중앙 높이**, 닫힘값을 물체 폭에서 자동
계산, 개폐 한계(약 80 mm) 초과 시 팔을 움직이기 전에 거부, place 후 물체 재배치.

### 6-2. 실측 3종 (실기체 준비물)

**① 홈 관절값** — 5-2에서 기록한 7개 값.

**② FINGER_OFFSET과 TABLE_HEIGHT**
- 자로 그리퍼 길이(플랜지 면 → 손끝)를 잰다 — 대략 0.13 m 근처.
- 직접 교시 모드에서 그리퍼 **끝을 테이블에 살짝 대고**, 교시 모드 해제 후:
  ```bash
  ros2 run tf2_ros tf2_echo base_link Link7
  ```
  Translation의 z를 기록 → `TABLE_HEIGHT = z − (자로 잰 그리퍼 길이)`
  (테이블이 베이스 설치면보다 낮으면 음수가 나온다. 예: −0.115)
- `FINGER_OFFSET = (자로 잰 그리퍼 길이) − 0.015` — 파지 중심(손가락 패드 중앙)은 손끝보다
  1~2 cm 위에 있으므로 보정. 측정 후 팔은 홈으로 복귀.

**③ 물체 좌표 A·B** — 자로 베이스 기준 거리를 잰다.
- 좌표계: **x = 로봇 전방(+), y = 로봇 왼쪽(+), 단위는 미터(m)!** — mm로 잰 값은 반드시 변환
  (412 mm → 0.412 m). 단위 혼동이 이 실습 사고 1순위다.
- 두 사람이 독립적으로 재서 교차 검증한다 — 로봇의 반복 정밀도는 ±0.05 mm지만 사람의 측정은
  수 mm~수 cm 흔들린다. 미션 오차의 대부분은 로봇이 아니라 자에서 나온다.

### 6-3. 실기체 실행

`scripts/real_pick_place.py` 상단의 **설정부를 실측값으로 수정**한 뒤 실행한다.
이 스크립트는 팔은 MoveIt(계획+충돌 검사), 그리퍼는 `rm_driver` 토픽(힘 제어 파지)으로 다루며,
**모든 팔 이동을 Plan → RViz 잔상 확인 → Enter → Execute**로 진행한다 — SOP ④가 코드 구조로
강제되어 있다.

```bash
# 터미널 1 (5절의 bringup이 떠 있는 상태 유지)
ros2 launch rm_bringup rm_75_bringup.launch.py

# 터미널 2 — 첫 시도: A 위 접근 자세까지만 가서 눈으로 정렬 확인
python3 scripts/real_pick_place.py --approach-only

# 정렬이 맞으면(그리퍼가 물체 바로 위) 전체 시퀀스
python3 scripts/real_pick_place.py
```

- 첫 시도를 접근 자세까지만 하는 이유: 좌표 측정 오차를 하강 전에 눈으로 잡아내기 위해서다.
  어긋나 있으면 스크립트의 `PICK_XY`를 몇 mm 단위로 수정 후 재시도.
- 시도 사이클(15분): 준비 2분 → 실행 5분 → 분석 5분 → **값 하나만** 수정 3분.
  좌표와 파지력을 동시에 바꾸면 무엇이 효과였는지 알 수 없다 — 변인 통제.
- **파지력 튜닝은 이분 탐색** — 확실히 놓치는 약한 값과 확실히 쥐는 강한 값을 먼저 찾고 중간값으로
  좁힌다. (힘 값 / 결과: 미끄러짐·성공·변형) 표를 남기면 그 표가 "힘 감각"의 증거다.

### 6-4. 실패 모드 도감 — 증상으로 원인 좁히기

| 증상 | 유력 원인 | 1차 처방 |
|---|---|---|
| 그리퍼가 물체 옆을 스치고 지나감 | 좌표 측정 오차 · 축 방향 혼동 | 재측정 + 2인 교차 검증 — 코드보다 **자를 먼저** 의심 |
| 잡았다가 이송 중 놓침 | 파지력 부족 · 파지 성공 확인 생략("허공 배달") | force 한 단계 ↑, 파지 결과 확인 후 다음 단계로 |
| 접근 중 테이블에 닿아 보호 정지 | 경유점 없이 직행 · 접근이 수직이 아님 | 물체 위 +10 cm 경유점 → 수직 하강 (실패의 90%가 여기) |
| Plan 자체가 실패 | 목표가 작업 반경 밖 · 자세 무리 · Scene 충돌 | 물체를 반경 2/3 안(약 40 cm)으로, 검증된 "아래 보기" 자세 재사용 |
| 놓는 위치가 매번 흩어짐 | 개방 타이밍이 이름 · 이송이 빠름 | 하강 완료 후 개방, 속도 스케일 한 단계 ↓ |
| 실기체 보호 정지 | 충돌 보호 (설계된 안전 동작) | 손대지 말고 담당자 콜 · 무엇을 하다 멈췄는지 기록 |
| `/joint_states`가 안 들어옴 | `udp_ip` 오설정 (1-2절) | config 확인 → rm_driver 재빌드 → 재실행 |
| 그리퍼 명령 무반응 | 토픽/필드 이름 상이 | `ros2 topic list \| grep gripper`, `interface show`로 실제 이름 확인 |
| 스크립트가 `timeout` 필드 오류 | 드라이버 버전별 메시지 차이 | 해당 필드는 스크립트가 자동으로 건너뛰도록 되어 있음 — 그래도 나면 `interface show` 결과에 맞춰 수정 |

### 6-5. 마무리 산출물

- 시퀀스 코드(수정한 좌표·힘 값 포함) + 실행 영상 + 파지력 시도 표 + 한 페이지 회고
  (① demo와 실기체가 가장 달랐던 지점과 원인 ② 다시 해도 그렇게 할 결정 하나 ③ 다음 기수에게 조언 한 줄)
- 잘 동작한 값들(홈 자세, FINGER_OFFSET, TABLE_HEIGHT, 접근 높이, 파지력)을 인수인계 노트로 남긴다.
